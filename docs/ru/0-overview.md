# Библиотека clarity

Библиотека `clarity` — декларативная библиотека для описания и синтаксического анализа интерфейсов командной строки (CLI) в программах на языке Yukino. В отличие от традиционных библиотек ручного анализа аргументов, `clarity` отделяет описание интерфейса от логики приложения и переносит его в специализированный файл схемы `.cty`. На этапе компиляции макрос транслирует схему в строго типизированные структуры аргументов, перечисление команд и компактный байткод рантайм-движка.

Библиотека предоставляет разработчику высокий уровень надежности и эргономики: исчерпывающее сопоставление команд через `switch`, автоматическое цветное форматирование справки, исправление опечаток в командах и флагах, валидаторы значений, интеграцию с переменными окружения и конфигурационными файлами, а также генерацию скриптов автодополнения для Bash, Zsh и Fish.

## 1. Введение в CLI для начинающих

Интерфейс командной строки (Command Line Interface, CLI) — это способ взаимодействия пользователя с программой посредством текстовых команд в терминале. 

### Анатомия вызова консольной программы

Рассмотрим типовой вызов утилиты:

```sh
mygit commit -m "первый коммит" --verbose src/main.ykn
```

Вызов состоит из следующих компонентов:
1. **Имя утилиты (`mygit`)** — имя исполняемого файла программы (в схеме задается директивой `app`).
2. **Подкоманда (`commit`)** — действие, которое программа должна выполнить. Каждая подкоманда может иметь собственные уникальные параметры (в схеме объявляется через `define commit`).
3. **Опция со значением (`-m "первый коммит"`)** — параметр, передающий значение. Имеет короткую форму (`-m`) или длинную (`--message`).
4. **Флаг-переключатель (`--verbose`)** — логический параметр (`bool`). Если он указан, флаг равен `true`, иначе `false`.
5. **Позиционный аргумент (`src/main.ykn`)** — аргумент, передаваемый без имени флага, определяемый своей позицией в командной строке (в схеме объявляется через `param`).

### Почему декларативная схема лучше ручного парсинга

При традиционном подходе разработчик вручную перебирает системный массив строк `args()`:
- Пишет циклы, условия `if / else` и ручные преобразования строк в числа и булевы флаги.
- Вручную форматирует тексты справки `--help` и следит за их актуальностью при изменении кода.
- Тратит время на обработку ошибок: что делать, если забыли передать обязательный аргумент или опечатались в имени флага.

С библиотекой `clarity` вы объявляете контракт интерфейса один раз в файле `.cty`. Процедурный макрос во время компиляции создает структуры данных и функции проверки, гарантируя, что программа получит корректно разобранные и строго типизированные значения.

## 2. Подключение: load clarity

Чтобы подключить библиотеку `clarity` к проекту, добавьте зависимость в секцию `[libs.runtime]` манифеста `yuki.toml`:

```toml
[libs.runtime]
clarity = { git = "https://github.com/shareui/clarity", tag = "0.1.0", package = "clarity" }
```

### Импорт в коде программы

В файле точки входа (`src/main.ykn`):

```yukino
load clarity: *
```

Доступные сущности:
- **Макрос схемы:** `#[clarity::scheme("путь/к/файлу.cty")]`.
- **Сгенерированные сущности:** функция `parse()`, функция `parse_args(cli_args)`, функция `try_parse()`, перечисление `Command`, структуры аргументов `<ИмяКоманды>Args`.
- **Рантайм-классы и функции:** `ClarityVm`, `VmResult`, `run_vm`, `run_vm_safe`, `Config`, `config_open`, `config_open_file`.
- **Генераторы автодополнения:** `generate_bash`, `generate_zsh`, `generate_fish`.
- **Рендереры оформления:** `render_command_help`, `render_app_help`, `render_version`.
- **Структура ошибок:** `ClarityRuntimeError`.

## 3. Архитектура и принцип работы

Схема работы `clarity` состоит из трех ключевых уровней:

1. **Декларативная схема (`.cty`):** разработчик объявляет метаданные приложения (имя, версию, описание), подкоманды, флаги с типами и значениями по умолчанию, позиционные параметры, валидаторы и ограничения.
2. **Макрос компиляции (`scheme`):** компилятор `yukino` при обработке атрибута `#[clarity::scheme("cli.cty")]` парсит файл схемы, проверяет семантическую корректность, компилирует схему в бинарный байткод и генерирует исходный код на языке Yukino:
   - Структуру `<Command>Args` для каждой объявленной команды с полями соответствующих типов (`bool`, `string`, `int32`, `float` и т. д.).
   - Перечисление `Command` с вариантами для каждой команды (`Command::Build(BuildArgs)`).
   - Функцию `parse() -> Command`, связывающую системные аргументы `args()` с виртуальной машиной и распаковывающую результат в сгенерированное перечисление.
3. **Рантайм-движок (`clarity_rt`):** виртуальная машина `ClarityVm` десериализует байткод, разбирает токены командной строки, автоматически обрабатывает `--help`, `-h`, `help <cmd>`, `--version`, сопоставляет опечатки через расстояние Левенштейна и выполняет валидаторы значений.

## 4. Быстрый пример

### Шаг 1. Создание схемы (`cli.cty`)

Создайте файл `cli.cty` в корне проекта:

```cty
app "mytool"
version "1.0.0"
about "Пример консольного приложения"

define build "Сборка целевого пакета" {
    --release, -r: bool = false "Режим оптимизации сборки";
    --output, -o: string = "app.bin" "Путь к выходному файлу";
    param target: string = "host" "Целевая архитектура платформы";
}

define run "Запуск собранного бинарника" {
    --port, -p: int32 = 8080 "Сетевой порт сервера";
    param file: string "Путь к исполняемому файлу";
}
```

### Что сгенерировал макрос (примерный код за кулисами)

На этапе компиляции макрос `#[clarity::scheme]` превращает этот файл в чистый код Yukino:

```yukino
// Структуры аргументов для каждой команды
public struct BuildArgs {
    release: bool
    output: string
    target: string
}

public struct RunArgs {
    port: int32
    file: string
}

// Единое перечисление всех команд
public enum Command {
    Build(args: BuildArgs),
    Run(args: RunArgs),
}

// Функция синтаксического анализа аргументов процесса
public fun parse() -> Command {
    // Внутренний вызов виртуальной машины clarity_rt
    ...
}
```

### Шаг 2. Использование в `src/main.ykn`

```yukino
load std.io: println
load clarity: *

#[clarity::scheme("cli.cty")]
fun clarity_init() { space }

fun main() {
    set cmd = parse()
    switch cmd {
        Command::Build(build_args) -> {
            println("Команда: build")
            if build_args.release {
                println("Режим: release")
            } else {
                println("Режим: debug")
            }
            println("Выходной файл: " + build_args.output)
            println("Архитектура: " + build_args.target)
        }
        Command::Run(run_args) -> {
            println("Команда: run")
            println("Порт: " + cast(run_args.port, "string"))
            println("Файл: " + run_args.file)
        }
    }
}
```

### Шаг 3. Запуск и проверка в терминале

```sh
# Вызов встроенной цветной справки
./mytool --help

# Запуск подкоманды с параметрами
./mytool build --release -o server x86_64

# Демонстрация работы подсказок при опечатках
./mytool bulid
# error: unrecognized subcommand 'bulid'
#   tip: a similar subcommand exists: 'build'
#
# For more information, try '--help'.
```
