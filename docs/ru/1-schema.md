# Язык схем Clarity (.cty)

Файлы схем с расширением `.cty` представляют собой декларативное описание интерфейса командной строки на специализированном предметно-ориентированном языке (DSL). Файл схемы компилируется процедурным макросом на этапе сборки и задает строгую грамматику параметров утилиты, избавляя от написания ручного кода разбора аргументов.

---

## 1. Сводная таблица директив схемы

| Директива | Область действия | Обязательность | Назначение |
| :--- | :--- | :--- | :--- |
| `app "<имя>"` | Заголовок схемы | **Обязательно** | Системное имя исполняемого файла для вывода строк `USAGE:`. При отсутствии компилятор возвращает ошибку 105. |
| `version "<версия>"` | Заголовок схемы | Опционально | Версия программы, выводимая при передаче флагов `--version`, `-V`, `-v`. |
| `author "<автор>"` | Заголовок схемы | Опционально | Сведения об авторе или организации. |
| `about "<описание>"` | Заголовок схемы | Опционально | Краткое описание назначения утилиты для главного экрана `--help`. |
| `default_flags true/false` | Заголовок схемы | Опционально | Автоматическое включение флагов `-h, --help` и `-V, --version` (по умолчанию `true`). |
| `config "<путь>"` | Заголовок схемы | Опционально | Относительный путь к файлу конфигурации TOML (в директории пользователя `~/.config/`). |
| `define * { ... }` | Тело схемы | Опционально | Блок **общих (глобальных) флагов**, доступных во всех подкомандах. |
| `define { ... }` | Тело схемы | Опционально | **Корневая команда** (выполняется при запуске утилиты без подкоманд). |
| `define <имя> { ... }` | Тело схемы | Опционально | Именованная **подкоманда** со своими флагами и позиционными параметрами. |
| `uncommon define <имя>` | Тело схемы | Опционально | Подкоманда, **изолированная** от глобальных флагов `define *`. |
| `config define <имя>` | Тело схемы | Опционально | Встроенная подкоманда управления конфигурационным файлом приложения. |

## 2. Разница между `define *`, корневой `define` и подкомандами

Это важнейшее концептуальное различие, которое необходимо понимать при проектировании интерфейса:

```
+---------------------------------------------------------------+
|                       Схема CLI (.cty)                        |
|                                                               |
|  1. define * { ... }             -> Общие флаги (--verbose)   |
|                                     (наследуются командами)   |
|                                                               |
|  2. define "описание" { ... }    -> Корневая команда          |
|                                     (вызов: ./app --flag)     |
|                                                               |
|  3. define build { ... }         -> Именованная подкоманда    |
|                                     (вызов: ./app build ...)  |
+---------------------------------------------------------------+
```

### 2.1 Общие флаги: `define * { ... }`

Блок `define *` объявляет флаги, которые должны быть доступны **в любой подкоманде** вашей программы (например, флаги подробного вывода `--verbose`, тихого режима `--quiet` или формата вывода `--json`).

Пример схемы:

```cty
app "cloudcli"
version "1.0.0"

// Общие флаги для всех подкоманд
define * {
    --verbose, -v: bool = false "Подробный вывод логов";
    --json: bool = false "Вывод в формате JSON";
}

define deploy {
    param env: string "Целевое окружение";
}

define status {
    --timeout: int32 = 30 "Таймаут запроса в секундах";
}
```

#### Что генерирует макрос:

```yukino
// Отдельная структура для общих флагов
public struct CommonFlags {
    verbose: bool
    json: bool
}

public struct DeployArgs {
    env: string
}

public struct StatusArgs {
    timeout: int32
}

// Варианты перечисления содержат и общие флаги, и флаги команды
public enum Command {
    Deploy(common: CommonFlags, args: DeployArgs),
    Status(common: CommonFlags, args: StatusArgs),
}
```

#### Ожидаемый ввод в терминале:

```sh
# Развертывание с длинным флагом общих настроек
./cloudcli deploy production --verbose
# В коде:
# common.verbose == true, common.json == false
# args.env == "production"

# Использование короткого флага -v
./cloudcli deploy staging -v
# В коде:
# common.verbose == true, common.json == false
# args.env == "staging"

# Запрос статуса с переопределением таймаута и выводом в JSON
./cloudcli status --timeout 60 --json
# В коде:
# common.verbose == false, common.json == true
# args.timeout == 60
```

> Если конкретная команда не должна принимать общие флаги, добавьте перед ней ключевое слово `uncommon`:
> ```cty
> uncommon define ping {
>     param host: string;
> }
> ```
> В сгенерированном коде команда `Command::Ping(args: PingArgs)` не будет содержать поля `common`.

### 2.2 Корневая команда: `define { ... }`

Корневая команда объявляется ключевым словом `define`, за которым **сразу следует описание в кавычках либо открывающая фигурная скобка `{`** (без имени команды).

Используйте корневую команду, если у вашей программы нет подкоманд (как у утилит `grep`, `cat`, `curl`), или если программа может вызываться напрямую без подкоманд:

Пример схемы:

```cty
app "minicat"
version "0.1.0"
about "Простая утилита вывода содержимого файлов"

define "Вывод содержимого файлов на экран" {
    --numbers, -n: bool = false "Нумеровать все строки";
    param file: string "Путь к исходному файлу";
}
```

#### Что генерирует макрос:

```yukino
public struct RootArgs {
    numbers: bool
    file: string
}

public enum Command {
    Root(args: RootArgs),
}
```

#### Ожидаемый ввод в терминале:

```sh
# Запуск с коротким флагом
./minicat -n document.txt
# В коде: args.numbers == true, args.file == "document.txt"

# Запуск с длинным флагом
./minicat --numbers /etc/hosts
# В коде: args.numbers == true, args.file == "/etc/hosts"

# Запуск без дополнительных флагов (используется дефолтное значение false)
./minicat readme.md
# В коде: args.numbers == false, args.file == "readme.md"
```

### 2.3 Именованные подкоманды: `define <name> { ... }`

Используются для утилит с несколькими режимами работы (как `git commit`, `git push` или `cargo build`):

```cty
app "pkgtool"
version "2.0.0"

define init "Инициализация нового пакета" {
    --name: string = "app" "Название проекта";
}

define publish "Публикация пакета в реестр" {
    --dry-run: bool = false "Тестовый запуск без отправки";
    param registry: string = "default" "Имя реестра";
}
```

#### Что генерирует макрос:

```yukino
public struct InitArgs {
    name: string
}

public struct PublishArgs {
    dry_run: bool
    registry: string
}

public enum Command {
    Init(args: InitArgs),
    Publish(args: PublishArgs),
}
```

#### Ожидаемый ввод в терминале:

```sh
# Инициализация с флагом по умолчанию
./pkgtool init
# В коде: args.name == "app"

# Инициализация с указанием имени проекта
./pkgtool init --name my_app
# В коде: args.name == "my_app"

# Публикация с позиционным аргументом
./pkgtool publish crates-io
# В коде: args.dry_run == false, args.registry == "crates-io"

# Публикация в тестовом режиме
./pkgtool publish internal --dry-run
# В коде: args.dry_run == true, args.registry == "internal"
```

### 2.4 Вложенные подкоманды: define внутри define (Nested Subcommands)

Для создания многоуровневых интерфейсов (таких как `git remote add`, `npm config set` или `docker container run`) библиотека `clarity` позволяет вкладывать блоки `define` внутрь других команд на любую глубину.

Пример схемы с вложенными подкомандами:

```cty
app "mytool"
version "1.0.0"

define config "Управление конфигурацией приложения" {
    --global, -g: bool = false "Использовать глобальный конфигурационный файл";

    define set "Установить значение параметра" {
        param key: string "Имя ключа конфигурации";
        param val: string "Новое значение ключа";
    }

    define get "Получить значение параметра" {
        param key: string "Имя ключа конфигурации";
    }

    define list "Показать все сохраненные настройки" {
        --json: bool = false "Вывод в формате JSON";
    }
}
```

#### Что генерирует макрос:

Для родительской команды создается перечисление подкоманд `<Parent>Subcommand`, а в структуру аргументов родительской команды добавляется опциональное поле `sub`:

```yukino
// Аргументы вложенных подкоманд
public struct ConfigSetArgs {
    key: string
    val: string
}

public struct ConfigGetArgs {
    key: string
}

public struct ConfigListArgs {
    json: bool
}

// Перечисление вложенных вариантов
public enum ConfigSubcommand {
    Set(args: ConfigSetArgs),
    Get(args: ConfigGetArgs),
    List(args: ConfigListArgs),
}

// Аргументы родительской команды
public struct ConfigArgs {
    global: bool
    sub: ConfigSubcommand?
}

// Главное перечисление
public enum Command {
    Config(args: ConfigArgs),
}
```

#### Использование в коде программы:

```yukino
switch cmd {
    Command::Config(cfg) -> {
        if cfg.global {
            println("Режим: глобальный файл настроек")
        }
        switch cfg.sub {
            ConfigSubcommand::Set(args) -> {
                println("Установка параметра: " + args.key + " = " + args.val)
            }
            ConfigSubcommand::Get(args) -> {
                println("Чтение параметра: " + args.key)
            }
            ConfigSubcommand::List(args) -> {
                if args.json {
                    println("{\"status\": \"all_configs\"}")
                } else {
                    println("Список всех настроек")
                }
            }
            null -> {
                println("Действие не указано. Запустите 'mytool config --help' для списка действий.")
            }
        }
    }
}
```

#### Ожидаемый ввод в терминале:

```sh
# Установка значения ключа
./mytool config set user.theme dark
# В коде:
# cfg.global == false
# args.key == "user.theme", args.val == "dark"

# Чтение значения с флагом родительской команды
./mytool config --global get user.theme
# В коде:
# cfg.global == true
# args.key == "user.theme"

# Вывод всех настроек в формате JSON
./mytool config list --json
# В коде:
# cfg.global == false
# args.json == true

# Просмотр справки родительской команды (показывает список доступных подкоманд)
./mytool config --help

# Просмотр справки конкретной вложенной подкоманды
./mytool config set --help
```

## 3. Определение флагов (Options / Flags)

Флаги объявляются внутри блока команды с префиксом двойного дефиса `--`.

### Синтаксис объявления флага:

```cty
--<длинное_имя> [, -<короткое_имя>] : <тип> [?] [ = <значение_по_умолчанию> ] [модификаторы...] ["описание"];
```

Правила обязательности компонентов флага:
- Длинное имя `--name`: **Обязательно**.
- Короткое имя `,-n`: **Опционально** (состоит из одной латинской буквы).
- Тип данных `: <тип>`: **Обязательно**.
- Модификатор `?` (nullable): **Опционально**. Если указан, в коде генерируется `T?`.
- Значение по умолчанию `= <значение>`: **Опционально**. Для типа `bool` по умолчанию устанавливается `false`, для `count` — `0`. Если значение по умолчанию **не указано** и флаг не является `?` (nullable), рантайм считает такой флаг **обязательным** (`[required]`), и программа завершится с кодом ошибки `2`, если пользователь его не передаст.
- Описание `"Текст"`: **Опционально**.

### Поддерживаемые типы данных:

| Тип в `.cty` | Тип в коде Yukino | Значение по умолчанию | Описание |
| :--- | :--- | :--- | :--- |
| `bool` | `bool` | `false` | Логический флаг-переключатель (`--release`) |
| `count` | `uint8` | `0` | Счетчик повторов флага (`-v` -> 1, `-vv` -> 2, `-vvv` -> 3) |
| `int32` | `int32` | обязателен или дефолт | 32-битное целое число (`--port 8080`) |
| `int` / `int64` | `int64` | обязателен или дефолт | 64-битное целое число (`--limit 100000`) |
| `float` / `float64` | `float64` | обязателен или дефолт | Число с плавающей точкой (`--ratio 0.75`) |
| `string` / `str` / `path` | `string` | обязателен или дефолт | Текстовая строка или путь к файлу (`--output file.txt`) |
| `string[]` / `path[]` | `string[]` | пустой массив `[]` | Повторяющийся флаг (`-i a.txt -i b.txt`) |
| `int[]` | `int32[]` | пустой массив `[]` | Повторяющиеся числовые аргументы |
| `enum { A, B, C }` | `string` | обязателен или дефолт | Выбор строго из фиксированного списка вариантов |

### Пример с флагами разных типов:

```cty
define server "Конфигурация сервера" {
    --daemon, -d: bool = false "Фоновый режим работы";
    --workers, -w: int32 = 4 "Количество рабочих потоков";
    --host: string = "127.0.0.1" "Адрес сетевого интерфейса";
    --log-level: enum { debug, info, warn, error } = "info" "Уровень логирования";
    --cert: path? "Путь к TLS-сертификату (опционально)";
    --tags: string[] "Теги для группировки процессов";
}
```

#### Что генерирует макрос:

```yukino
public struct ServerArgs {
    daemon: bool
    workers: int32
    host: string
    log_level: string
    cert: string?
    tags: string[]
}
```

#### Ожидаемый ввод в терминале:

```sh
# Базовый запуск с дефолтными значениями
./server_app server
# В коде:
# args.daemon == false
# args.workers == 4
# args.host == "127.0.0.1"
# args.log_level == "info"
# args.cert == null
# args.tags == []

# Запуск с передачей флагов, нескольких тегов и опционального сертификата
./server_app server -d -w 8 --host 0.0.0.0 --log-level debug --cert /etc/ssl/cert.pem --tags web --tags api
# В коде:
# args.daemon == true
# args.workers == 8
# args.host == "0.0.0.0"
# args.log_level == "debug"
# args.cert == "/etc/ssl/cert.pem"
# args.tags == ["web", "api"]
```

### 3.4 Переопределение и отключение стандартных флагов справки и версии

По умолчанию компилятор автоматически генерирует обработку стандартных информационных флагов:
- `-h`, `--help` — вывод цветной справки текущей команды и завершение процесса (`exit(0)`).
- `-V`, `-v`, `--version` — вывод версии приложения и завершение процесса (`exit(0)`), если задана директива `version`.

Библиотека предоставляет два гибких механизма управления этим поведением:

#### 1. Переопределение собственными флагами (Flag Override)

Если вы объявляете в схеме собственный флаг с именем `help`, `h`, `version`, `V` или `v`, рантайм **автоматически отключает** стандартную реакцию на этот флаг и передает управление вашему коду программы.

Наиболее частый практический пример — использование флага `-v` для уровня подробности логов (`verbose`), а не для вывода версии:

```cty
app "logger"
version "1.0.0"

define * {
    // Переопределяем флаг -v для уровня подробности логов:
    --verbose, -v: count = 0 "Уровень подробности логов (-v, -vv, -vvv)";
}

define run {
    param target: string "Файл для запуска";
}
```

#### Ожидаемый ввод в терминале:

```sh
# Флаг -v обрабатывается как пользовательский счетчик, а не как версия!
./logger run -vvv app.bin
# В коде: common.verbose == 3, args.target == "app.bin"

# Для версии по-прежнему работают флаги -V и --version
./logger --version
# Вывод: logger 1.0.0
```

Если же вам требуется кастомная обработка флага справки:

```cty
define export {
    --help, -h: bool = false "Показать расширенную справку экспорта";
}
```

Тогда при вызове `./app export --help` рантайм не завершит процесс принудительно, а передаст управление в тело `main`, выставив `args.help = true`.

#### 2. Полное отключение через `default_flags false`

Если вашей утилите не нужны встроенные флаги справки и версии (например, для строгого соответствия протоколу внешнего инструмента или для бинарников без текстового интерфейса), укажите в заголовке схемы `default_flags false`:

```cty
app "raw_service"
default_flags false

define {
    --port: int32 = 8080 "Сетевой порт";
}
```

При установке `default_flags false`:
- Рантайм не перехватывает вызовы `-h`, `--help`, `-v`, `-V` и `--version`.
- Флаги справки не отображаются в текстах `FLAGS:`.
- При попытке пользователя передать `--help` программа выведет ошибку о неизвестном аргументе (`error: unexpected argument '--help' found`) с кодом завершения `2`, если только этот флаг не объявлен вами вручную.

## 4. Определение позиционных параметров (`param`)

Позиционные параметры передаются без имен флагов и сопоставляются строго по порядку их следования в командной строке.

### Синтаксис объявления:

```cty
param <имя> : <тип> [?] [ = <значение_по_умолчанию> ] [модификаторы...] ["описание"];
```

Правила обязательности компонентов параметра:
- `param <имя>`: **Обязательно**.
- Тип данных `: <тип>`: **Обязательно**.
- Модификатор `?` (nullable): **Опционально**.
- Массив `[]` (вариативный параметр): **Опционально**. Обозначает список из одного или нескольких аргументов.
- Значение по умолчанию `= <значение>`: **Опционально**. Если значение не указано и параметр не nullable, он считается **обязательным** (`[required]`).

> [!IMPORTANT]
> Если параметр является вариативным массивом (`param files: string[]`), он **обязан быть последним** позиционным параметром в команде. Попытка объявить другие позиционные параметры после вариативного приведет к ошибке компилятора 103.

### Пример:

```cty
define copy "Копирование файлов" {
    --force, -f: bool = false "Перезаписывать существующие файлы";
    param source: string "Исходный файл";
    param destination: string "Целевая директория";
}

define archive "Создание архива из нескольких файлов" {
    param target_archive: string "Имя архива";
    param inputs: string[] "Список упаковываемых файлов";
}
```

#### Что генерирует макрос:

```yukino
public struct CopyArgs {
    force: bool
    source: string
    destination: string
}

public struct ArchiveArgs {
    target_archive: string
    inputs: string[]
}
```

#### Ожидаемый ввод в терминале:

```sh
# Простое копирование
./fileutil copy src/main.ykn dist/main.ykn
# В коде:
# args.force == false
# args.source == "src/main.ykn"
# args.destination == "dist/main.ykn"

# Копирование с флагом перезаписи
./fileutil copy -f config.old config.new
# В коде:
# args.force == true
# args.source == "config.old"
# args.destination == "config.new"

# Создание архива из переменного количества файлов
./fileutil archive bundle.tar file1.txt file2.txt file3.txt
# В коде:
# args.target_archive == "bundle.tar"
# args.inputs == ["file1.txt", "file2.txt", "file3.txt"]
```

## 5. Модификаторы и ограничения флагов

Модификаторы позволяют задавать зависимости между параметрами, альтернативные источники значений и переопределять сообщения об ошибках:

### 5.1 Источники из переменных окружения: `env(...)`

Если пользователь не передал флаг в командной строке, значение автоматически читается из переменной окружения:

```cty
define connect {
    --token: string env(API_TOKEN) "Токен авторизации в сервисе";
    --host: string = "localhost" env(SERVICE_HOST) "Хост службы";
}
```

#### Ожидаемый ввод в терминале:

```sh
# Передача значения напрямую через CLI
./connect --token "secret-xyz"

# Либо через переменную окружения (флаг опущен)
export API_TOKEN="secret-xyz"
./connect
# В коде: args.token == "secret-xyz", args.host == "localhost"
```

### 5.2 Источники из конфигурационного файла: `config(...)`

Если флаг не передан в командной строке и отсутствует в переменных окружения, значение читается из TOML-конфигурации приложения:

```cty
define build {
    --output: string config(build.output) = "dist/app" "Каталог сборки";
}
```

### 5.3 Зависимости флагов: `requires`

Указывает, что данный флаг может использоваться только в том случае, если передан другой зависимый флаг:

```cty
define publish {
    --signed: bool = false "Подписать пакет";
    --key: path requires signed "Путь к закрытому ключу для подписи";
}
```

#### Ожидаемый ввод в терминале:

```sh
# Корректный вызов (оба флага присутствуют)
./pkg publish --signed --key cert.pem

# Ошибочный вызов (передан только зависимый флаг)
./pkg publish --key cert.pem
# error: the argument '--key' requires '--signed'
```

### 5.4 Конфликты флагов: `conflicts`

Запрещает совместное использование двух несовместимых опций:

```cty
define test {
    --all: bool = false conflicts target "Запустить все тесты";
    --target: string conflicts all "Запустить конкретный тест";
}
```

#### Ожидаемый ввод в терминале:

```sh
# Корректный вызов одного из флагов
./test_runner test --all
./test_runner test --target auth_tests

# Ошибочный вызов обоих флагов одновременно
./test_runner test --all --target auth_tests
# error: the argument '--all' cannot be used with '--target'
```

### 5.5 Пользовательское сообщение об ошибке: `error "..."`

Позволяет переопределить стандартное сообщение рантайма на понятный текст:

```cty
define run {
    --port: int32 error "Порт должен быть валидным числом от 1 до 65535" range(1, 65535);
}
```

## 6. Валидаторы значений

Валидаторы проверяют корректность введенных пользователем данных до того, как управление перейдет в функцию `main`:

| Валидатор | Применимость | Назначение |
| :--- | :--- | :--- |
| `range(min, max)` | Числовые типы (`int`, `float`) | Проверяет вхождение числа в отрезок `[min, max]` включительно. |
| `pattern("<регулярка>")` | Текстовые типы | Проверяет соответствие строки регулярному выражению (через `std.regex`). |
| `min_len(n)` | Строковые типы | Минимальная длина строки в символах. |
| `max_len(n)` | Строковые типы | Максимальная длина строки в символах. |
| `one_of("a", "b", ...)` | Строковые типы | Допускает значение только из перечисленного списка. |
| `exists` | `path`, `string` | Проверяет существование файла или папки на диске (через `std.fs.path_exists`). |
| `parent_exists` | `path`, `string` | Проверяет существование родительской директории пути. |

### Пример использования валидаторов:

```cty
define deploy {
    --workers: int32 = 4 range(1, 64) "Количество воркеров (от 1 до 64)";
    --version-tag: string pattern("^v[0-9]+\\.[0-9]+\\.[0-9]+$") "Тег версии вида v1.0.0";
    --config-file: path exists "Путь к существующему файлу конфигурации";
    --output-file: path parent_exists "Файл отчета (директория должна существовать)";
}
```

#### Ожидаемый ввод в терминале:

```sh
# Корректный вызов со всеми валидными значениями
./deployer deploy --workers 8 --version-tag v2.1.0 --config-file app.toml --output-file dist/log.txt

# Ошибка при выходе числа из допустимого диапазона
./deployer deploy --workers 128
# panic: flag '--workers' value 128 out of range [1, 64]
```

## 7. Группы параметров (`or`, `and`)

Группы позволяют объединять несколько флагов логическими связками.

### 7.1 Взаимоисключающая группа: `or`

Пользователь может указать максимум один флаг из группы:

```cty
define format "Форматирование вывода" {
    or output_mode ? {
        --json: bool = false "Вывод в формате JSON";
        --yaml: bool = false "Вывод в формате YAML";
        --xml: bool = false "Вывод в формате XML";
    }
}
```

- `or <имя> ?` — знак вопроса означает, что группа **опциональна** (пользователь может не указывать ни одного флага, либо указать максимум один).
- `or <имя>` (без знака вопроса) — группа **строго обязательна**: пользователь обязан передать ровно один флаг из перечисленных.

#### Что генерирует макрос:

```yukino
public struct FormatArgs {
    json: bool
    yaml: bool
    xml: bool
}
```

#### Ожидаемый ввод в терминале:

```sh
# Корректный запуск с одним из флагов группы
./formatter format --json
# В коде: args.json == true, args.yaml == false, args.xml == false

# Ошибка при попытке передать несколько несовместимых флагов
./formatter format --json --yaml
# error: the argument '--json' cannot be used with '--yaml'
```

### 7.2 Связанная группа: `and`

Если передан хотя бы один флаг из группы, пользователь обязан передать все остальные флаги этой группы:

```cty
define login "Авторизация в системе" {
    and credentials ? {
        --username: string "Имя пользователя";
        --password: string "Пароль учетной записи";
    }
}
```

#### Что генерирует макрос:

```yukino
public struct LoginArgs {
    username: string
    password: string
}
```

#### Ожидаемый ввод в терминале:

```sh
# Корректный вызов (оба взаимозависимых флага указаны)
./auth login --username admin --password secret
# В коде: args.username == "admin", args.password == "secret"

# Ошибка при передаче только одного флага из группы
./auth login --username admin
# error: the following required flag was not provided: '--password'
```
